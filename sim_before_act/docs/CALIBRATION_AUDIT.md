# Simulator-vs-calibration audit (read-only)

Question: why does the real recording report `shoulder_lift` ≈ −103° while the MJCF joint range is ±100°?

Status of this document: **audit only**. No calibration file, recording or model was changed. No limit was
widened, no value clipped, no offset added. Nothing here validates an SO-101 digital twin or says anything about
real-world failure prediction.

## 1. Short answer

* **Verified:** there is no unit, ordering or formula bug that explains −103°. The recorded value is exactly what
  LeRobot 0.6.1 produces from the user's follower calibration, and it lies **inside that calibration's own range**
  (raw tick 859 vs `range_min` 837).
* **Verified:** the MJCF limit (±100°) is a **fixed number inherited from a third-party CAD/URDF model**, not
  measured on this arm. The user's calibration gives ±105.3° for shoulder_lift (leader ±104.7°). Two different
  physical arms/calibrations simply have different travel.
* **Verified:** the same kind of mismatch exists for `wrist_flex` (recorded up to +100.8° vs ±95°).
* **Verified:** the over-limit values are not scattered noise. Frames 0–412 (13.8 s of 19.9 s) hold shoulder_lift
  at a constant −103.4° and wrist_flex at +100.8°; both are beyond their MJCF limits in the same 411 frames. That is
  a static pose, consistent with the arm resting at/near its mechanical stops (front camera frame 0 shows the
  robot at the mat edge; whether it is folded or against its stops is not established by the image).
* **Hypothesis (not verified):** the MJCF's "virtual zero = middle of the joint range" and the user's
  calibration zero (= midpoint of the range the user swept by hand) coincide only if the sweeps reached the same
  physical stops. A per-joint zero offset of a few degrees is therefore plausible but **unmeasured**.
  It needs a physical measurement (§7), not a guess.

No conclusive software conversion bug was found, so **no code change was made to the conversion.**

`info.json` stores feature names (`*.pos`) and shapes only. **It does not record units, calibration id/hash or
normalisation mode.** The dataset therefore does not prove it was recorded in degrees; that is inferred from
LeRobot's default `use_degrees=True` and the plausible value range, and is flagged `ASSUMED` by our importer.

## 3. Conversion chain

```
Present_Position (raw ticks, 0..4095, after the motor's Homing_Offset)      [LeRobot: get_observation]
  → _normalize (calibration JSON)                                           [dataset value, "observation.state"]
       arm joints (MotorNormMode.DEGREES):  deg = (raw − mid) · 360 / 4095,  mid = (range_min + range_max) / 2
       gripper (RANGE_0_100):               v   = 100 · (raw − range_min) / (range_max − range_min)   (bounded)
  → sim_before_act ActionContract.to_sim_rad
       arm:     rad = deg2rad(deg)                      (no offset, no sign flip)
       gripper: rad = lo + (v/100)·(hi − lo),  lo = −0.1745, hi = 1.745  (MJCF joint range)   ← UNVALIDATED
  → MuJoCo joint qpos / position-actuator ctrl (radians)
```

Notes: `_normalize` for DEGREES is **not clamped**; the degree zero is the midpoint of the user's recorded range, not
a fixed physical reference. `drive_mode` is 0 for every joint (follower and leader), so no sign inversion is applied
by LeRobot. `max_relative_target=10` in `run.sh` clips each sent action step relative to the present position, so a
recorded `action` is the *clipped value that was sent*, not necessarily the leader's raw value.

Static-pose evidence: lift is −103.4° for frames 0–412 (5th and 50th percentile both −103.4) and wrist_flex

(0.119, −0.006, 0.185) m with no robot self-contact; the clipped variant is ≈1.6 cm away. This shows the pose is
kinematically plausible in the model; it does **not** show it matches reality.

## 6. Interpretation of the evidence

Verified:
* The recorded −103.4° is a correct LeRobot-normalised value for raw 859 under the user's calibration.
* The MJCF ±100° is a design constant, not measured here; it is narrower than this arm's calibrated range.
* The recording spends 69 % of its frames at a static pose beyond the MJCF limits on two joints.

Hypotheses (each needs evidence):
* H1: the MJCF zero pose and the calibration-midpoint zero differ by a few degrees per joint.
* H2: the user's hand-swept calibration extremes include slack/over-travel beyond the reference unit's stops.
* H3: the arm was recorded starting from the folded rest pose against (or near) its stops.
* H4: the MJCF gripper range/direction does not match LeRobot's 0 = closed / 100 = open.

What the offline pipeline did right: it rejected the real window with `INVALID_INPUT` because the action was outside
the model limits. That rejection is correct *behaviour* for an unvalidated model; it is not a finding about the real
robot's safety.

## 7. Unresolved questions that require physical measurement

Not performed; no hardware was connected or moved.
1. External-reference angle of each joint at the pose where the calibration midpoint is defined versus the MJCF zero
   pose (inclinometer/protractor with the follower **powered down and moved by hand only if the user chooses**).
2. Whether the folded rest pose at lift = −103.4° / wrist_flex = +100.8° is at the mechanical stop or merely near it.
3. Direction of each joint (sign) relative to the MJCF axis, by reading LeRobot values while the user moves the
   leader/follower by hand.
4. Gripper: physical opening vs value (0…100), and which MJCF angle corresponds to closed.
5. Actuator response (position-gain, delay) for sim-to-real, not addressed here.
6. Calibration id/hash that was active when the recording was made.

## 8. Proposed corrections (NOT applied)

1. Add a per-joint `sim_offset_deg`/`sign` table to the action contract, populated only from measurement (§7.1, 7.3),
   with source and date; refuse to run if absent for a real record.
2. Define simulator limits for this arm from measured physical stops, recorded with provenance, keeping the
   reference-model limits as a separate, documented set. Do not widen the MJCF limits to fit the recording.
3. Record raw ticks (`Present_Position`) alongside normalised values in future recordings, plus calibration id +
   sha256 in dataset metadata, so state conversion is auditable.
4. Settle the gripper mapping (measured open/closed angles) and remove the 10° ambiguity between our mapping and the
   existing script.
5. If a software bug is later identified, the smallest fix will be a change in `ActionContract.to_sim_rad`, with a
   regression test asserting the converted value for a fixed raw/normalised input pair taken from the measurement.
   None is identified today.

## 9. Interpretation items reviewed (code and docs updated)

* **Gate statistic:** the gate compares the **point estimate** of the simulated failure fraction with the threshold
  (`EXECUTE` only if `fraction < threshold`, strict). The Wilson upper bound is **not** used. Confirmed in
  `runtime/gate.py` and by test `test_gate_uses_point_estimate_not_wilson_bound_and_trace_states_rule`.
* **Traces** now carry `decision.decision_rule` (statistic, strict comparison, `uses_wilson_upper_bound: false`,
  threshold, `threshold_calibrated`, the demo-value note, the separate safety-violation rule when configured and the
  other required conditions).
* **Wilson interval** is Monte-Carlo sampling uncertainty under the chosen rollout/perturbation model only. It does
  not include simulator or calibration mismatch (such as the one in this audit) and does not demonstrate physical
  safety. This is now stated in `verification.interval_note` and in the trace limitations.
* **Task failure vs safety violation** are reported as separate fractions and counts. The gate's primary rule is on
  the aggregate (either kind of failure); the optional `reject_on_safety_violation_fraction` rule is separate.
* **Timing** is preliminary: one machine, no warm-up or repetition protocol, boundaries not formally defined. Stated in
  `verification.timing_note` and trace limitations; it is not an E3 measurement.
